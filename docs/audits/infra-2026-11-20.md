## What is right, and worth not breaking

Verified this pass, not assumed:

- **All GitHub Actions are pinned to full commit SHAs.** Zero unpinned `uses:`.
- **No `pull_request_target`**, and no `github.event.*.body`/`head_ref`
  interpolated into a `run:` block. The classic CI injection routes are absent.
- **`ci.yml` declares top-level `permissions:`.**
- **Admin token comparison is constant-time** — length check, then XOR
  accumulate (`tokenMatches`, worker/src/index.js). No early return on first
  mismatching byte.
- **Wallet sign-in has real replay protection**: a nonce with an expiry, the
  issue time inside the signed message, the domain in the message, expired
  nonces reaped on a schedule, and `/api/nonce` + `/api/session` rate-limited to
  10/min per IP.
- **Rate limiting is broad**: 61 route groups declared, 57 keyed by IP or wallet.
  `ipKey` collapses IPv6 to the /64, so one subscriber cannot rotate through a
  whole allocation to look like billions.
- **D1 access is parameterised** — 215 `.bind()` calls; the handful of
  concatenations are fixed table names from code, never request input.
- **No secrets in logs**, no seed phrase or private key stored server-side, and
  no inbound webhooks at all, so there is nothing to forge.
- **One CSP, from one place** (fixed 2026-11-05 in #18) and no third-party
  script host in it.
- **The agent surface is clean.** One committed skill (`elfa-ai`), added before
  any agent had access. No `curl … | bash`, no injection text, no unexpected
  binaries, and no agent commit ever touched `.claude/`.

## Findings

### [HIGH] INFRA-11: CI gates GitHub Pages, but production is Vercel and ungated

**Confidence:** 9/10 · **Phase:** 3 — CI/CD · **Category:** OWASP A08 Integrity Failures
**Location:** `.github/workflows/ci.yml:326-350`, `vercel.json`

**Description:** `ci.yml`'s deploy job is correctly gated — `needs: [secrets,
program, worker, site]`, so a red check stops it, and its own comment says this
was the point. But that job publishes to **GitHub Pages**. Production is served
by **Vercel**, which deploys from its own GitHub integration on every push to
`main`. `vercel.json` has no `git`, `github` or `ignoreCommand` key, so nothing
tells Vercel to wait for a check. The gate guards a host that is not production.

Branch protection does not cover the gap either: two pushes to `main` during
this session returned `remote: Bypassed rule violations for refs/heads/main: 4
of 4 required status checks are expected`. The account's admin bypass lets a
push through with no check having run.

**Exploit scenario:**
1. Any push to `main` — an agent's, a mistaken one, a compromised token's —
   starts a Vercel production deploy immediately.
2. CI runs *in parallel*, not as a gate. The site is already live by the time
   `Site` or `Secret scan` reports.
3. A red build therefore reaches users. The 2026-11-05 incident is the shape of
   this: a deploy intended to stop third-party stalls shipped with two of its
   own goals unmet, and nothing blocked it.

**Evidence:**
```
$ python3 -c "...json.load(open('vercel.json'))..."
vercel.json top-level keys: ['$schema', 'headers', 'redirects', 'rewrites']
# no git / github / ignoreCommand key

$ git push origin main
remote: Bypassed rule violations for refs/heads/main:
remote: - 4 of 4 required status checks are expected.
```

**Remediation:** two parts, both small.
1. Gate Vercel on CI with an ignore command, so a deploy aborts unless the
   commit's checks are green:
   ```json
   "ignoreCommand": "gh api repos/solquicks/solquicks/commits/$VERCEL_GIT_COMMIT_SHA/check-runs --jq '[.check_runs[]|select(.conclusion!=\"success\")]|length==0' | grep -q true"
   ```
   Or, with less machinery: turn off Vercel's git auto-deploy and publish from
   the gated CI job via the Vercel CLI.
2. Stop admin bypass from applying to this rule — in GitHub's ruleset, clear
   "Allow specified actors to bypass" (or add yourself to it only deliberately).
   A required check that the owner routinely bypasses is a check in name only.

**Priority:** P1 — this week.

```

3a7180a  worker: unknown /api paths are 404, not 401; session routes listed
627da0f  worker: paths outside /api answer 404, not 401
```

Their character is reassuring — they cite issue IDs (I5, I11, L1, L11), they
harden rather than add, and spot-checks confirm real fixes landed (the IPv6
/64 rate-limit key is one). But none has had a second pair of eyes, and one of
them, #17, was already found wrong in two silent ways: a CDN dependency left in
place and a duplicate CSP quietly overriding the header. Both failed without an
error anywhere. The same author wrote the payment-binding and points-exploit
commits, where silence costs money rather than fonts.

**Exploit scenario:** not an attacker path — a correctness-and-trust one. #13
claims USDC payments are bound to reference, time, exact amount and all treasury
accounts. If any one of those four is not actually enforced, a replayed or
mis-targeted payment credits a booking it did not pay for, and nobody finds out
from a log, because the commit that was supposed to prevent it reports success.

**Remediation:** read them, in this order: `48427ae` (#13, payment binding),
`00be3fa` (#11, points exploit), `f512c2d`/`fc82e1b` (#16, swap route options).
For each, trace the money path end to end rather than reading the diff, and
check whether the added tests assert the new guarantee or only the happy path.
A review task for exactly this is already drafted and waiting to be started.

**Priority:** P1 — this week. Nothing is known broken; it is unverified, which
is a different thing and the reason to look.

### [MEDIUM] INFRA-13: `.gitignore` does not cover the file types that leak keys

**Confidence:** 8/10 · **Phase:** 1 — Secrets · **Category:** Secret exposure

**Description:** `git check-ignore` is authoritative, and it says:

| path | ignored? |
|---|---|
| `worker/.dev.vars` | yes |
| `program/target/deploy/moon_stake-keypair.json` | yes |
| `collectible/authority.json` | yes |
| **`.env`** | **no** |
| **`.env.local`** | **no** |
| **`*.pem`** | **no** |
| **`*.key`** | **no** |
| **`id.json`** | **no** |

The specific files that have mattered so far are covered — each added after it
caused a problem. The general classes are not. This repo is public and has
already leaked one secret key by exactly this route (INFRA-08, September), and
`git add -A` is in routine use in this project, including by me.

**Exploit scenario:**
1. Anyone — a person or an agent — runs `solana-keygen new -o id.json`, or drops
   a `.env` beside the worker while debugging.
2. The next `git add -A && git commit` takes it. Nothing refuses: these names
   are not ignored.
3. It is pushed to a public repo. GitHub's push protection catches some token
   formats but **not** a Solana keypair byte array, which is why INFRA-08
   happened in the first place.

**Remediation:** append to `.gitignore`:
```gitignore
# Classes, not just the files that have already bitten us: this repo is public
# and a keypair array is not something GitHub push protection recognises.
.env
.env.*
!.env.example
*.pem
*.key
*.p12
id.json
*keypair*.json
```
**Priority:** P2 — this month. Two minutes, and it closes the route that
produced the only real secret exposure this project has had.

### [LOW] INFRA-15: upstream credentials travel in URL query strings

**Confidence:** 6/10 · **Phase:** 4 / 8 · **Category:** A09 Logging / data exposure

**Description:** The worker reaches Helius as
`https://mainnet.helius-rpc.com/?api-key=…` at 17 call sites, and Telegram as
`https://api.telegram.org/bot<token>/…`. Both are server-side, both read from
Worker secrets, and neither is in a client bundle, so this is not an exposure
today. It is a shape worth knowing: a query string is the part of a request most
likely to end up in someone else's log, an error message or a traceback. A
header does not have that property.

**Remediation:** Helius accepts the key as a header; move it there when those
lines are next touched. Telegram's API only takes it in the path, so that one
cannot be changed. Not worth a dedicated change.
**Priority:** P3 — backlog.

## Re-verified: INFRA-08 from 2026-09-12

The September audit found a 64-byte Solana secret key committed in `873a858`
(2026-09-01) at `program/target/deploy/moon_stake-keypair.json`, belonging to
`9vVtZ3Qdpz7JdbB5PwVdUmhPoVmUNwQuXeuRmpQxVpNJ`. It rated it **LOW** and closed
it as deliberately accepted. That rating rests on the key being worthless, so it
is worth re-testing rather than inheriting. Checked on chain today:

| address | mainnet | devnet |
|---|---|---|
| `9vVtZ3Qd…` (the leaked key) | nothing deployed | nothing deployed |
| `DSWFRcF4…` (the declared program) | nothing deployed | **deployed**, upgradeable |

The reasoning holds. The leaked key is not the declared program's, nothing is
deployed at its address on either network, and nothing in the tree references
it. `program/target/` is gitignored and the current program keypair is untracked
— confirmed by `check-ignore`. **Still LOW, still correctly accepted.**

Two things the September audit could not have said:

- The commit holding the dead key is reachable from `origin/main` and every
  remote branch, so it is permanently public. That does not change the rating —
  a worthless key stays worthless — but it does mean rotation is the only
  remedy available, exactly as that audit concluded.
- The live devnet program's upgrade authority is
  `Fwj6BE9ea7cexku9vhAwDwhhMsHN4bzzhnT2baKRayDk`, a single key rather than a
  multisig. Fine for devnet. `MAINNET.md` already lists deciding this before
  mainnet as an open item, so it is tracked, not a finding.

## False positives filtered, and why

Recorded so the next pass does not re-raise them:

1. **`fetch(src.url)` at index.js:3194** — looks like SSRF; `src` iterates a
   hardcoded three-element `SOL_PRICE_SOURCES` array. No user input.
2. **`'SELECT * FROM ' + t` at index.js:4973** — looks like SQL injection; `t`
   iterates a literal array of seven table names, on a token-gated admin route.
3. **`'SELECT … FROM ' + kind.table`** (6 sites) — `kind` comes from the fixed
   `CHECKOUTS` object, never a request.
4. **`Access-Control-Allow-Origin: '*'` at 4544/4555** — it is the Moon Ranger
   artwork image proxy. Public images must load cross-origin; correct as-is.
5. **`worker/` has no lockfile** — it also has no dependencies at all
   (`dependencies: {}`, `devDependencies: {}`). Nothing to pin.
6. **`JUPITER_API_KEY: 'jup-test-key'`** in `worker/test/swap-api.test.mjs` —
   test fixture, hard-exclusion 5.
7. **64-number arrays in `games/moon-rangers/assets/index-*.js`** — the
   keypair-shaped pattern matching minified 3D geometry.

## For the audit itself

Two notes on method, both limits on what is above.

The guard hook refuses Bash commands naming key or secret files, so Phase 1 ran
from scripts in the scratchpad with its patterns in a separate file. One
follow-up script was correctly refused for extracting a key to derive its
pubkey; I dropped that step rather than working around it, which is why the
INFRA-08 re-verification rests on on-chain state and the September audit's
derivation rather than on my own.

And the correction at the top is the useful lesson: I raised a CRITICAL from a
filename, and the previous audit's own notes disproved it. Reading the prior
report before writing the new one is not bookkeeping — it is what caught the
error.
